ELI5 · 图解

.scratch/ 是什么

它不是「临时草稿夹」。它就是这个仓库的计划、决定和任务本身 —— 只不过全部写成 Markdown 文件，放在一个看不见的文件夹里。

先看地图：一个 feature 一个抽屉

`.scratch/` 就是一个工单台。每个 feature 一个抽屉，抽屉里放着这个 feature 的全部纸。

抽屉之间不共享文件；所有抽屉的清单写在最上面那份 .scratch/README.md。

.scratch/ ├── README.md ← 索引：一行一个 feature │ └── tool-declaration-visibility/ ← 一个 feature 一个抽屉 ├── seed.md ← 种子：还没成形的一个想法 ├── map.md ← 决策图：一张迷雾里的路线图 ├── spec.md ← 构建计划：定下来的「怎么做」 ├── issues/ ← 票：一票一个文件 │ ├── 01-research-tool-table-shape.md │ ├── 04-grilling-visible-shape.md │ └── 10-docs-glossary-and-walkthrough.md ├── research/ ← 一手调研（对源码/官方文档查出来的事实） └── prototype/ ← 一次性原型（画出来看看长什么样）

抽屉里的纸，只有四种角色

seed 是「还没成形」，map 是「在决定」，spec 是「定了」，票是「在做」。

🌱 seed.md 想法

一个想法、一份意向、一段对话的折叠。

里面没有票 —— 只有 seed，说明这件事还没被访谈过。

抬头没有 Status: 行。

本仓库：33 份。

🗺️ map.md 决策图

一件事太大、单个会话装不下时画的路线图。

几节正文：目的地 / 笔记 / 已定的决定 / 尚未明确 / 任务清单。

它只产决定，不产代码。

本仓库：19 张图。

📐 spec.md 构建计划

一次追问访谈折出来的那几节决定：问题陈述、用户故事、实现与测试决定、明确的「明确不做」。

它是实现票的来源，票只指回它、不重述理由。

本仓库：59 份。

🎫 issues/NN-slug.md 票

最小单位。一票一个文件，从 01 编号，永不合成一个文件。

每票自包含：做完一票就能把它那份上下文扔掉。

本仓库：511 张。

research/ —— 事实

去源码、去官方文档查出来的事实，一个 claim 一条出处（文件:行号）。

本仓库：26 个目录。

prototype/ —— 形状

一次性的、看完就扔的原型，用来回答「长什么样」这种画出来才说得清的问题。

本仓库：14 个目录。

spec / map 抬头的 Status

那不是状态，是完成度计数：35/35 done、9 resolved + 7 done。

票全部落地后必须改成实际完成度 —— 停在 ready-for-agent 会让下一个人以为还没开工。

parity.md / report-*.md

某张图的附属账：一张对照表、一份 HTML 报告。给图当证据，不参与状态流转。

一张票长什么样

开头那几行，就是它的全部身份证。

Type: 这张票是「哪一类活」

前三类产决定，后两类产东西。

research 找事实

去源码和官方文档查事实，产出 research/NN-*.md。

AFK：不需要人在场，后台跑完就交回来。

prototype 出形状

画一帧、做一次性原型，回答「长什么样」。

HITL：维护者要过目。

grilling 问到底

一轮轮追问，逼近真正要拍的那个决定。

HITL：不许 agent 自问自答。

task 要动手的决定

前面几类之外、需要动手才能定下来的决定。

implement 动手实现

图走完之后由 /to-tickets 拆出的构建切片。

它不是图的一部分：由 /implement 认领。

本仓库实际用量

implement 303 · grilling 92 · research 32 · prototype 25 · task 8。

状态怎么流转

这里有三条状态机。认错了词，就以为票走错了路。

状态值什么意思谁写
ready-for-agent票写全了，可以交给一个不用人在场的 agent 去跑。拆票时写死；实现票的起点。
claimed有人占下了这张票，正在做。这是并发会话之间的「我不碰」。开工前写。是 中途状态，不算完成。
resolved决策票有答案了 —— 答案在票底的 ## 作答 里。决策票的终点。
done实现票做完了，验收项都过了。实现票的终点。
ready-for-walkthrough能自动化的部分全做完了，只等人在真终端里逐项走查。它不是 ready-for-human —— 那是「必须人来实现」，这是「人来看一眼」。
needs-triage needs-info ready-for-human wontfix分诊那套：等人评估 / 等人补料 / 必须人来做 / 不处理。照 /triage 技能走。本仓库目前实际只用了实现/决策那两套。

交棒：折成构建计划

/wayfinder
画图、逐张推进
/research · /prototype · /grilling
handoff 交棒
  • 图走完 ≠ 全部做完。 设计票全关掉，图就算走完，哪怕实现票还开着。
  • 图留着当决策记录。 所以 map.md 和 spec.md 可以同时存在。
  • 交棒不能绕开。 直接开实现票，会丢掉决定之间的那些链接。
  • 被排掉的方向要关掉，不实现。 决策票一改形状，对应的票就改或关。

右侧面板里看到的是什么

面板读的就是这些 Markdown 文件，不是另一份数据库。

本地 markdown 后端只有一条折叠规则：

resolved / done / closed / completed → 关闭
其它一切 → 打开

  • map.md 是编号 00 的那张票，永远置顶；子票是 01、02……
  • 面板的「被挡住」= 票顶的 Blocked by: 那几行。
  • 面板的「已认领」= Assignees: 那行 / claimed 状态。
  • 新写的票会带上 ## Comments 与 ## Answer 两段骨架 —— 那是面板认得的位置。

三条护栏脚本

纸多了会烂，所以有脚本盯着。

scripts/wayfinder-check.py

拿图的「任务清单」跟 issues/ 里的文件对账：条目数必须相等，每张子票都要有 Type: / Status: / Part of: / Blocked by:。

对不上就非零退出 —— 不许把「被拒」读成「通过」。

scripts/check-language.py

中文只许上升：翻过的段落不许被改回英文。

一份 tracker 文件都没有也会报错。

scripts/check-doc-size.py

给活文档定「压表达」规则：单元 ≤500 字符，只删「别处已有一份的复述」。

不删任何文件。

数票的两条命令

ls .scratch/*/issues/*.md | wc -l

grep -h '^Status:' .scratch/*/issues/*.md | sort | uniq -c

六个绕口的词

slug

文件名的短标识：issues/04-grilling-visible-shape.md 里那截。磁盘上的定位符，叙述里要写名字。

feature 目录

tracker 的存放单位。一个 feature 一个目录，feature 之间不共享文件。

交棒 handoff

图走完那一刻，把图上互相链接的决定收束成 spec。绕开它直接开票，会丢掉那些链接。

认领 claim

开工前把票占下来。叙述说「认领」，磁盘上写 claimed。

阻塞边 Blocked by

票顶一行记的依赖边。列出的每张票都到终态，这张票才解阻塞。

frontier

下一批可以动的票：open、没被阻塞、也没被认领，编号最小的当选；Type: implement 一律跳过。

一句话记住

seed 是想法，map 是决定，spec 是计划，票是干活

状态就三句：决策票 claimed → resolved；实现票 ready-for-agent → done（只等人看就停在 ready-for-walkthrough）；分诊 另有一套五个词。
