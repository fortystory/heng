# 三个方向各出一帧：工具声明在界面上看得见，长什么样

Type: prototype
Status: claimed
Part of: ../map.md
Blocked by: 01, 02

## 问题

[工具表那份账](../research/01-tool-table-shape.md) 与
[三条既有通道](../research/02-channels.md) 两张事实票已经把底账铺好了。接下来要回答的是
**「工具声明在界面上以什么形态可见」** —— 三个方向各自长什么样，**并排**看一遍。

为什么需要原型而不是直接讨论：这一件事是**「看起来怎么样」**的问题。
`ask_user_question` 的用法说明有 896 字符（[票 01](../research/01-tool-table-shape.md) 第 2 节），
整张表在 `description` 上合计 5881 字符、在参数 schema 上是 1.5–2 万字符量级 ——
**「一次看全表」不是一页纸**。抽象地讨论「画一行还是画 N 行」很容易谈空，画出来才谈得清。

## 要出哪几帧

**按真实字符格画，不许编造。** 尺寸与排法照今天的实现：详情覆盖层的尺寸**从布局常量算出来**
（`src/render/layout.rs` 的 `overlay_area` / `DETAIL_MAX_WIDTH` / `DETAIL_PADDING`），
**别自己拍一个数** —— [`trace-ledger` 的原型票 07](../trace-ledger/issues/07-prototype-inspector.md)
就是这么做才可信的。折行排法与参数面同一套（`folded_text`）。

三帧：

1. **帧 A · 通道三（per-call）**：工具调用详情覆盖层的 `Schema` 面**加上用法描述** ——
   先画 `description`，再画参数 schema。要画出**一条长声明**（`ask_user_question`）与
   **一条短声明**（`write_file`，63 字符）两种长度下这个面读起来什么样；也要画出**今天那个
   「工具表里没有「<名字>」，这次调用的声明查不到」**那一行长什么样（它会不会被 description
   挤得更难认）。
2. **帧 B · 通道二（会话级记录）**：仿系统提示词那一行 —— 转录上一条**可点开**的记录，
   点开是全表。至少给出两个变体：
   - **B1 · 一行 + N 行**：转录上就一行（写明多少条），点开是整张表逐条摊开；
   - **B2 · N 行**：转录上就是 N 行，每个工具一行，点开是那一条的完整声明。
   两种都要画**第一屏**放得下什么（19 条内建 + N 条动态，一屏 26 行）。
   再给**来源名**写死一句话候选 —— 系统提示词那条把「按当前代码拼，不进事件流」写进了来源名
   （`src/render/wording.rs:1566`），工具声明那条要不要照抄这个做法。
3. **帧 C · 通道一（进流注入）**：把整张表当一条上下文注入推进去，在转录上的样子 —— 以及
   **它进模型上下文之后多出来的那一份**长什么样。**这一帧是为「明确排除它」服务的**：
   排除要有依据，依据就是它长什么样。

**顺带把「一次看全表」的两种读法画出来**：全部 `description` 逐条列出（19 × 平均 300 字符）
vs 只列名字与首行（其余点开再看）。

## 判定

**维护者过帧判定够用**，然后票底给 `## 作答`：每帧各说明它给出了什么线索、哪一处读不出来、
以及**它偏向哪个方向**。判断不许只写「好看」—— 要写清**哪一个具体读法被帧证明了 / 被帧否掉了**。

这一步只提高讨论的保真度，**它不选方向** —— 选方向是
[工具声明在界面上以什么形态可见](04-grilling-visible-shape.md) 的活。
