> 文档要写的是**实际行为** —— 哪一张形态落地就写哪一张；两张都落地就都写。

## 目标

- 把落地的形态写进**逐面文档**：工具声明在界面上以什么形态可见，一句不多一句不少。
- 把「**声明**」与「**参数 schema**」这两个说法在文档里**分清** —— 今天
  `docs/render.md` 那句「声明（发给 provider 的那份 JSON Schema）」只对了三分之一。
- 词表按 06 的结论收口；真机走查条目写好（有没有人走查过，是这张图走没走完的一部分）。

## 现状（开工前先复核）

- `docs/render.md` 要动的三处：「检视器的面」那张分派表（`:534-540`）、「系统提示词」那一节
  （`:493-501`，那是 09 的先例）、`Schema` 面那一节（`:544-551`，今天那句措辞失准）。
- 词表：[`CONTEXT.md`](../../../CONTEXT.md) 里今天只有「元工具」与「动态工具」两条的 `_Avoid_`
  提过工具表，**没有自己的条目**；「工具声明」也没有条目（研究 02 第 3 节）。
- 真机走查清单：[`docs/tui-manual-checklist.md`](../../../docs/tui-manual-checklist.md) —— 新条目
  接在最后一条之后。
- 文档纪律：新增或改写的 `docs/**` 要过 `scripts/check-doc-size.py` 的压表达规则（单元 ≤500）。

## 具体行为

1. **逐面文档**：写清「工具声明在界面上以什么形态可见」——落在哪个面 / 哪条记录上、点开是什么、
   那句「今天这张表」在哪儿、重放时看到的是什么。写的是**现状**，不搬 spec 的理由与备选方案。
2. **措辞分清**：`docs/render.md` 与 `CONTEXT.md` 里「声明」与「参数 schema」各指什么，写准。
3. **词表**：按 06 的结论立条目（**新概念才立条目** —— 若这次只是把已存在的东西显示出来，可能
   一条都不用立）。
4. **走查条目**：一条真机走查（按现有条目的写法：编号、一句判断标准、怎么做），把「看得见」这件事
   在**真终端**里验一遍。
