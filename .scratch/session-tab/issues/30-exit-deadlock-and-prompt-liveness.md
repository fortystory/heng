# 30: 退出流程不再死锁，提示请求跨轮保活

Type: implement
Status: done
Blocked by: 23, 28
Part of: ../map.md

**要打通的行为**：`Ctrl-D` 与 `/quit` 按下去**真的把进程带走**。退出这件事一旦卡住，屏幕上
的一切手势（按键、点击会话页）都会静默失效 —— 它是所有交互的前置。同时那行提示只该发一份，
不能每轮定时器重新发一次。

**来源**：维护者报告（2026-10-12 第三轮：「`ctrl-d` 不能退出」「不能正常切换会话，点击没反
应」）；[spec.md](../spec.md) §1；票 [`20`](20-click-to-switch.md)、[`23`](23-exit-gate-and-ctrl-c.md)、[`28`](28-ctrl-d-never-swallowed-and-asks-twice.md)。

## 验收

- [x] `Ctrl-D` 双击退出：进程结束、退出码 130、终端交还干净
- [x] `/quit` 退出：进程结束、退出码 0（TUI 与 `--plain` 两条前端各一遍）
- [x] 退出之后不存在「界面还在、按什么都静默失效」的状态
- [x] 退出流程里没有握手死锁：主循环先放掉自己那份渲染写端，再 await 渲染任务
- [x] 提示请求跨 `select` 轮次保活（一次只发一份，拿到一行才换下一份）
- [x] 真机回归：`scripts/tui-startup-check.py` 6/6 绿

## 实现记录（2026-10-12）

### 根因一：退出死锁 —— 主循环握着自己的渲染写端去 await 渲染任务

`RenderChannel::shutdown` 的契约是「等**每一个**写端消失」（票 13 的注释写着这件事，还写着
「调用方同样得先把自己的那份放掉」），而主循环在 573 行拿的那份 `render`（给闸门拒绝、取消
回执、装载提示用的）在退出流程里仍然活着 —— 渲染任务于是永远等不到 `Closed`，而主循环在
`shutdown().await` 上等它：两头顶着。`[DEBUG-hx91]` 日志的形状是 `shutdown-begin` 之后
**没有** `shutdown-end`，进程不退、也不再回到 `select`。

未修复的二进制上 pty 实测（临时诊断脚本：起 heng → 点页签 → 点会话行 → 按 `Ctrl-D` ×2 →
再点两处）：先点页签、点会话行都正常（宿主表读数 `1 场 → 2 场`），按过 `Ctrl-D` ×2 之后进程
还活着，而**此后点会话行、点页签一律没有反应**（读数停在 `2 场`）。维护者报的那两条症状是同一
个死锁，不是两件事。

修复：退出流程第一句 `drop(render)`，放在广播 `Close` 之前。

### 根因二：提示请求每轮重发 —— 输入被一份没人等的 reply 接走

主循环原来写的是 `tokio::select! { line = console.prompt() => … }`。`prompt()` 是
「发一条 `ConsoleRequest::Prompt` + await 它的 oneshot」，而 select 每轮（含那 80ms 的忙闲
定时器）都会重建这个 future —— 上一份请求的应答端随之被丢掉。前端那一侧于是分层：

- **`--plain`**：每个请求都真去读一行（`spawn_plain_console_with`），我们打进去的 `/quit`
  会被一份已经没人等的 reply 接走 —— **稳定无效**。
- **TUI**：渲染器把最新一份 reply 记在 `prompt_reply` 里，输入多数时候能对上，**偶发丢失**。

修复：把那 future 提到循环外保活（局部别名 `LineFuture<'_>`，`Option` 存着），拿到一行之后
才重新武装 —— 那时它确实完成了，留着再 poll 是未定义行为。

### 验证

- 修复前：`scripts/tui-startup-check.py` 7/7 红；未修复二进制上复现「`Ctrl-D` 之后点击全失效」
- 修复后：`python3 scripts/tui-startup-check.py target/debug/heng 1` → **0/6 red**
- `cargo test` 全绿

### 顺带：那份真机脚本自己已经与票 23/28 脱节

它不是「产品一直坏」的证据，而是**守卫失灵**：锚点还写 `ctrl-c`（空闲提示行现在只写
`ctrl-d 退出`）、出口清单里还有「`ctrl-c` 双击退出」（票 23 之后 `Ctrl-C` 只取消）、退出码一律
期望 0（`Ctrl-D` 走 130）、而且拿**原始 wait status** 去比退出码（130 会被读成 33280）。这一轮
把锚点、出口清单、退出码分档与就绪判据一起校准，它重新成为能红的那条检查 —— 本次死锁就是它
（`busy` 轮）与 `.cache/diag-freeze.py` 一起钉住的。

## 欠账

- 提示保活只覆盖主循环这一处。`CliActor` 一侧若还有「每轮重建同一个请求」的 await，属于同一
  类缺陷，值得单独排查一次。
- 会话页点击的**真机**端到端仍没有进 `cargo test`：这一轮用一次性 pty 脚本覆盖过（起一场
  TUI、点页签、点行、断言宿主表读数递增且主列换场），脚本随诊断结束删掉了。要不要把它做成一
  份正式的 `scripts/` 检查（SGR 鼠标序列 + 屏幕仿真）由票 09 定。
