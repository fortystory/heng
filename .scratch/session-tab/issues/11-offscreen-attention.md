# grilling：后台会话有事时的场外通知

Type: grilling
Status: resolved
Blocked by: —
Part of: ../map.md

## 问题

票 04 定了**场内**的提示：后台会话跑出需人答的东西时状态变 `AwaitingHuman`，列表页画 `?`、提示行说一句，`Ctrl-D` 退出被拒时还给一个可点入口。但那些都要求人**正看着这个终端**。

**场外**（人在别的窗口、别的机器上干活）怎么知道这个进程里有会话在等？现在唯一沾边的是终端标题：`.scratch/terminal-title/` 已经存在，而票 01 起终端标题认**当前会话**的四段 `<路径> · <标题> · <状态> · <目标名>`（丢序已定：目标名 → 标题 → 状态词）。

本票是这张图 `尚未明确` 里「场外通知」那一条升级来的。

## 需要定

1. **终端标题要不要认「别的会话在等」**：认的话它读哪里（宿主表的状态快照）、插在票 01 那四段的哪一处（会不会被丢序规则挤掉）、多场同时待答时写哪一场。
2. **要不要做桌面通知**：`.scratch/desktop-notifications/seed.md` 只有意向、`src/` 里没有实现。若要做，它属于**这张图**还是另开一张（本图 destination 是「会话页签的决策集」）。
3. **要不要别的东西**：提示音、进程退出码、`heng sessions` 里列「有几场在等」。
4. **触发面**：「有事」只算**待答**，还是后台会话**跑完一场回合**也算（人在等结果）。
5. **节流**：后台会话会反复进出待答态，通知要不要去重、只报第一场、或只在「从无到有」时响一次。

## 作答

2026-10-12 定完：两轮 grilling（5 + 4 问），另有一份只读代码调研（终端标题实现、状态通道、进程边界）。
以下契约**自足**。

**先纠两处事实**（调研查出，票面据此写过）：

- 终端标题**现状是三段** `<路径> · <状态> · <目标名>`（`.scratch/terminal-title/spec.md` §1；
  `wording::terminal_title` 签名只有 `cwd` / `home` / `state` / `goal`，`src/render/wording.rs:2127-2151`）。
  票 01 §7 定的**四段**（加 `<标题>`）与 `SessionTitled` 在 `src/` 里**都还没实现**。**本票的规则在
  两代形态下都成立**（它只改状态段那一段的取值）。
- 票 04 设计的宿主表 / 每会话 `watch<SessionState>` / `RenderEvent::SessionState` 在代码里
  **零命中** —— 那是本票的实现前提（先有票 04，才有「别的会话在等」这件事可读）。

### §1 认：把「别的会话在等」放进**状态段**

`title_state(replaying, pending, busy)`（`src/render/wording.rs:2063-2073`）现在只有三个 **bool**，
全部只描述**当前前台这一场**。扩展后的**状态段取值表**（优先级从高到低，**取第一个成立的**）：

| 优先级 | 条件 | 状态段写 |
|---|---|---|
| 1 | **后台**有会话 `AwaitingHuman`（≥1） | `N 场待答`（N = 后台待答场数） |
| 2 | 前台正在历史重放 | `重放中`（既有） |
| 3 | 前台自己有待答 | `等你`（既有） |
| 4 | **后台**有会话在未读窗口内刚跑完一场回合（≥1） | `N 场跑完`（N = 未读场数） |
| 5 | 前台在跑回合 | `运行中`（既有） |
| 6 | 都没有 | 空（省略整段，既有） |

- **段数不变、位置不变**：不新增段、不挤标题。票 01 的**丢序表一字不动**（从右往左依次丢
  目标名 → 状态段 → 路径退基名 → 硬截断到 40 列，`terminal-title` spec §3）—— 于是「还有几场在等」
  **最后才被丢掉**，这正是它该有的份量。
- **多场时写场数，不写哪一场**：标题不回答「哪一场」，那是会话页（票 02 的 `?` 标记）与
  提示行的活。
- **N 只算后台**：前台自己的待答沿用既有的 `等你`、前台在跑沿用 `运行中` —— 于是**单会话行为
  一字不变**（现状三段标题在单会话下完全不变）。

### §2 「跑完一场回合」这条边沿：在消费侧从电平快照推

「待答」是**电平**（状态一直停在 `AwaitingHuman`，随时可读）；「刚跑完」是**边沿**。而票 04 §4 的
渲染通道是 `broadcast`、容量 1024、满了静默丢（`src/render/mod.rs:75` 的 `let _ =` 与 `:273`，
丢帧只被叙述成一行诊断、**不补送**）—— 所以边沿不能靠它。

**契约**：宿主表每场一个 `watch<SessionState>`（票 04 §3 选 `watch` 的理由正是「保最新不丢」）；
**主循环每帧**（脉冲已经在跑）读一遍全部会话的状态，与上一帧的快照比对，自己推出
`RunningTurn → Idle` 这条边沿。**不新增通道。**

- 代价如实写进契约：一帧（60 ms）内 `运行 → 空闲 → 又运行` 翻两次会漏一次 —— 而「跑完」漏报
  一次无关紧要（它不像待答那样阻塞着谁）。
- 明确**不选**的两条：新增一条 mpsc「注意力队列」（新通道 + 新背压规则，只为一条通知）；
  复用现有 broadcast（丢了没人知道）。

### §3 未读的寿命、去重与节流

- **待答是电平**：`AwaitingHuman` 持续期间状态段一直写着它，不需要去重。
- **「N 场跑完」是未读语义**：保持到**用户下一次键盘或鼠标输入**，或**那一场又开跑**
  （`Idle → RunningTurn`）。人在别的窗口干十分钟回来，提示还在。
- **谁维护未读**：未读集合住在**主循环**（它持宿主表，知道「哪一场又开跑」）；「用户已读」由
  渲染器在**任意键盘 / 鼠标输入**时经它既有的上游队列回一条（`TuiState.events` 那条
  `FrontEndEvent` 通道，`src/render/tui.rs:1111`、`take_events` `:6439`），主循环收到就清空。
  两个消失条件因此都成立。
- **不需要额外节流**：标题只在**真变了**才重写 OSC（`sync_title` 与 `last_title` 比对，
  `src/render/tui.rs:2585-2592`；绘制路径 `:617-632`）；电平 + 未读集合本身已经幂等。

### §4 标题之外：只把「进程已经持有的信息」送到标题

本票**只做**这一件事。它的边界正好是：信息已经在宿主表里（票 04 的状态快照），本票只给它一个
**场外的表达**。别的东西见 §5、§6。

### §5 桌面通知：**另开一张图**

- 本图的 destination 是「会话页签的决策集」；桌面通知是**渲染器之外的子系统**（通知通道、
  跨平台、失焦检测、配置开关），与页签无关。
- [`.scratch/desktop-notifications/seed.md`](../../desktop-notifications/seed.md) 的四个待谈分叉
  （通道选哪个、触发点集合、要不要只在失焦时发、配置默认值与平台退化）**都是那张图的问题**。
  本票只把它的**触发点这一半对齐**：那张图该收的触发点是「需要人答」与「回合跑完」——与本票 §1
  的两种事同源（seed 自己也点了这两个时刻）。
- seed 里那句「缺的是把它送出去」在本票之后**仍然成立**：标题只是替换了本进程 `OSC 0` 所写的
  内容，不是新通道。
- 已在该 seed 里留一条指针（2026-10-12，票 11 的裁决）。

### §6 明确不做

- **提示音**：`src/` 里 `bell` 零命中，`\x07` 只作 OSC 序列的终止符；无先例，且与通知同族。
- **进程退出码按待答调整**：现状只分 0 / 130（`src/cli.rs:2696-2702`）；退出闸门只管「有回合在跑」
  （票 04 §7），待答的会话退出后流停在那里、下次 `-c` 续 —— 不新增第三个退出码语义。
- **`heng sessions ls` 列「有几场在等」**：它是**另一个进程**（`src/cli.rs:3510-3519` 的 `sessions_ls`
  → `observe::list`），宿主表只在活着的交互进程内存里；`observe.rs` 的模块文档自己写着「每个视图
  都是对事件流的一次 group-by，绝不是新的采集点」。要让它算出来就得落盘一份「谁在等」，而那违反
  「不造第二处真相」（冻结项 4 的立场）。
- **焦点检测**：终端拿不到可靠的失焦信息 —— 不做，一视同仁。
- **通知通道的实现**：归新图（§5）。

### §7 落点与要改的既有行为

- `wording::title_state`（`src/render/wording.rs:2063-2073`）：入参从三个 bool 扩成「前台三个 bool +
  后台待答场数 + 后台未读场数」（形状由实现选）。
- `wording::terminal_title`（`:2127-2151`）：只扩状态段的取值表；**丢序那一串回退不动**。
- `TuiState::title()`（`src/render/tui.rs:2489-2496`）：不再只读自己的 `replay` / `pending` / `busy`；
  后台那两个数由**主循环**经既有的循环→前端请求通道推给它（照 `ConsoleRequest::RunState` /
  `Muted` / `Catalog` 的先例，`src/render/input.rs:133`）——**渲染器不直接读宿主表**。
- `sync_title`（`:2585-2592`）与绘制路径（`:617-632`）**不动**：仍然只在真变了才写 OSC。
- 上游队列加一个「用户已读」手势（`FrontEndEvent`，`src/render/tui.rs:1111` 一带）——见 §3。

**交出去**：桌面通知整件事 → 另开一张图（`.scratch/desktop-notifications/seed.md` 已留指针）；
`docs/render.md` 的终端标题那一段若有改动 → 票 09。

不多发，`terminal-title` spec §4–§6）。
